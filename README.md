# 客服回复幻觉检测

## 1. 任务背景

团队的智能客服系统偶尔会"说瞎话":回复用户时编造不存在的优惠政策、给出错误的退货地址、杜撰产品参数。本工具对客服回复批量检测"幻觉",并与知识库比对定位问题。数据:`task4_replies.json`(20 条回复,每条含用户问题、系统回复、知识库)、`task4_ground_truth.json`(人工标注结果)。

## 2. 幻觉分类体系

通过对 20 条样本的分析,将幻觉定义为:**回复中包含与知识库矛盾、知识库中不存在、或超出系统能力的实质性错误陈述**。共分 6 类,严重程度按对用户的潜在危害分为 紧急 > 高 > 中 > 无:

| 类别 | 定义 | 严重程度 | 样本中的例子 |
| --- | --- | --- | --- |
| 安全误导 | 与知识库安全/健康警示相悖的建议,可能造成健康风险 | 紧急 | h13 面膜含视黄醇衍生物(孕妇需咨询医生),回复却说"孕妇可以放心使用" |
| 事实编造 | 编造与知识库矛盾或无依据的客观事实:产品参数、材质、地址、品牌关系、门店等 | 高 | h02 蓝牙 5.0→5.3;h06 PU 革→头层牛皮;h07 杜撰退货地址;h11 杜撰线下门店;h15 杜撰品牌关系;h17 USB-A→Type-C |
| 政策编造 | 编造不存在的政策、优惠或服务承诺:退货/发票/发货政策、优惠券、折扣等 | 高 | h01 7 天退货→30 天;h04 编造纸质发票;h05 编造满 300 减 50 券;h08 编造顺丰/48h;h19 编造学生 9 折 |
| 能力越界 | 声称执行了系统不具备的操作并编造具体结果(查物流、查退款、改地址、升工单) | 高 | h03 编造包裹位置;h10 编造退款进度;h14 声称已改地址;h18 声称已升级工单 |
| 信息遗漏 | 不直接矛盾,但遗漏关键限定信息导致结论实质失真、可能误导用户 | 中 | h20 知识库"30% 用户反馈偏大半码",回复却说"尺码标准不偏" |
| 非幻觉 | 回复与知识库一致或为合理转述 | 无 | h12 支付方式一致;h16 色差说明与知识库一致 |

与 ground_truth 的 8 种标注相比,本体系做了归并:GT 的"参数编造/信息编造"并入"事实编造","政策编造/政策偏差/优惠编造"并入"政策编造",其余(能力越界、安全误导、信息遗漏)一一对应。

## 3. 检测方法

**主方法:LLM 检测(DeepSeek deepseek-chat)**。将每条回复的 `{用户问题, 系统回复, 知识库}` 交给 LLM,要求按分类体系输出结构化 JSON 判定。

Prompt 设计的关键规则(见 `taxonomy.py` 的 `build_system_prompt()`):

1. 逐条比对回复与知识库,找出矛盾、杜撰或关键遗漏;
2. 知识库为「无(...)」表示系统不具备该能力/接口——回复若声称已执行并给出具体结果,判"能力越界";诚实说明无法操作则判非幻觉;
3. 回复与知识库一致或为合理转述,即使列举不完整(如支付方式少列一两种)也判非幻觉;
4. 知识库"未标注/未提及"某信息时,回复无依据地肯定,判编造;
5. 只有当遗漏会导致实质性误导时才判"信息遗漏";
6. 回复同时犯多种错误时,选危害最大的类别。

调用方式:OpenAI 兼容协议(`https://api.deepseek.com/chat/completions`),`temperature=0` + JSON mode 保证输出稳定可解析;仅用标准库 `urllib`,零第三方依赖;失败自动重试 3 次。

**兜底方法:规则模式(mock,`--mock` 参数)**:覆盖能力越界、安全误导、优惠编造、"未标注"四类明显模式,无 API 时可用,但召回率有限(见下节对比)。

**流程**:`taxonomy.py`(分类体系)→ `detector.py`(`LLMDetector` / `MockDetector`)→ `main.py`(批量检测)→ `evaluate.py`(对照 ground_truth 验证)。

| 精确率 Precision | **100%** | 100% |

各 GT 类型检出率均为 100%(参数编造 4/4、能力越界 4/4、信息编造 3/3、政策偏差 2/2、优惠编造 2/2、政策编造 1/1、安全误导 1/1、信息遗漏 1/1)。逐条对比详见 `results/evaluation_report.md`。

规则模式漏检 10 条(h01、h02、h04、h06、h07、h08、h11、h15、h17、h20),全部集中在需要"细粒度数值/事实比对"的类型上——纯规则难以覆盖开放式矛盾,这正是引入 LLM 的原因。

## 5. 误判分析:哪些 case 容易误判

本次 LLM 检测无实际误判,但以下 5 类边界 case 是潜在的误判高发区(规则模式的实际漏检印证了其中大部分):

1. **"遗漏型"幻觉(h20)——最容易漏检**。回复"尺码标准不偏"与知识库"30% 用户反馈偏大半码"不构成直接矛盾,GT 标注自己也注明"边界较模糊"。若检测器只做矛盾检测不做遗漏判断,必漏。缓解:分类体系单独设立"信息遗漏"(中严重度),并限定"仅在实质误导时才算"。
2. **"半对半错"型(h04、h08)——容易被正确部分蒙蔽**。h04 电子发票说法正确但纸质发票是编造的;若检测器只判断"是否提到正确内容"就会放过。缓解:规则 1 要求逐条比对、逐项核实。
3. **"无依据肯定"型(h09、h15)——无直接矛盾可抓**。知识库"未标注 NFC"、"未提及品牌关系",回复却斩钉截铁地肯定。这类幻觉需要"证据缺失即编造"的推理,而不是矛盾匹配。缓解:规则 4。
4. **能力越界型(h03、h10、h14、h18)——依赖对「无(...)」标记的理解**。若 prompt 不解释该标记,模型可能把"无"理解为"没有信息"而漏判,或把诚实拒绝误判为幻觉。缓解:规则 2 明确标记语义与正反例边界。
5. **非幻觉负例(h12、h16)——容易误报**。h12 少列了花呗/信用卡,h16 是对知识库的转述;若"遗漏即幻觉"的规则过严,会把这两条误报。缓解:规则 3 明确"列举不完整、合理转述不算幻觉"。

另外,LLM 输出不稳定性也是误判来源:temperature=0 + JSON mode + 校验归一化(非法类别回退、非法严重度按类别默认值)降低了格式类错误。

## 附:文件结构与用法

```
幻觉检测/
├── task4_replies.json          # 输入:20 条客服回复
├── task4_ground_truth.json     # 输入:人工标注
├── taxonomy.py                 # 幻觉分类体系 + 检测 prompt
├── detector.py                 # LLMDetector(DeepSeek)/ MockDetector(规则兜底)
├── main.py                     # 批量检测入口
├── evaluate.py                 # 对照 ground_truth 计算指标
├── .env                        # API Key(不入库,gitignore 已忽略)
└── results/
    ├── detection_results.json          # LLM 检测结果(含 evidence)
    ├── detection_results_mock.json     # 规则模式结果
    └── evaluation_report.md            # 验证报告
```

```bash
python main.py              # LLM 检测
python main.py --mock       # 规则兜底检测
python evaluate.py          # 对照 ground_truth 验证
```

API Key 配置:在项目根目录创建 `.env` 写入 `DEEPSEEK_API_KEY=sk-xxx`,或设置同名环境变量。
